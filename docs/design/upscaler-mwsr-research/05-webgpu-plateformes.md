## 1. External textures (`importExternalTexture({source: VideoFrame})` → `texture_external`)

### 1.1 What WGSL allows on `texture_external` (verified)
Sources: WGSL spec source `wgsl/index.bs` (https://gpuweb.github.io/gpuweb/wgsl/, main 2026-10-10) and Tint's intrinsic table `src/tint/lang/wgsl/core.def` / `core/core.def` (https://raw.githubusercontent.com/google/dawn/main/src/tint/lang/core/core.def, main 2026-10-10), which is what Chrome actually compiles.

- Definition (§6.6.4): "An External texture is an opaque two-dimensional float-sampled texture type similar to `texture_2d<f32>` but potentially with a different representation. It can be read using textureLoad or textureSampleBaseClampToEdge built-in functions, which handle these different representations."
- Exactly three overloads exist:
  - `textureDimensions(texture: texture_external) -> vec2<u32>`
  - `textureLoad(texture: texture_external, coords: vec2<C>) -> vec4<f32>` with C ∈ {i32, u32}; no level parameter.
  - `textureSampleBaseClampToEdge(texture: texture_external, sampler: sampler, coords: vec2<f32>) -> vec4<f32>` (also exists for `texture_2d<f32>`).
- **No** `textureSample`, `textureSampleLevel`, `textureSampleGrad/Bias`, `textureGather`, `textureNumLevels` overloads for `texture_external` (absent from both the spec table and core.def). Any sampler (filtering or not) is accepted; the spec: "The sampler provided to textureSampleBaseClampToEdge is used to sample the underlying textures."
- Clamp rule (§17.7 `textureSampleBaseClampToEdge`): coordinates are clamped to `[half_texel, 1 - half_texel]`, `half_texel = vec2(0.5)/vec2<f32>(textureDimensions(t))`; "independent of the sampler's addressing and filter modes, wrapping will not occur." Only the base level is sampled.
- `textureGather` on regular textures: `textureGather(@const component, texture_2d<T>, sampler, coords[, @const offset])` → `vec4<T>` (4 texels), T ∈ {f32,i32,u32} (core.def lines 1010–1045).

### 1.2 What the WebGPU spec says about the import (verified)
Source: `spec/index.bs` (https://gpuweb.github.io/gpuweb/, main 2026-10-10), §6.4, §6.4.1, §6.5, §3.11.
- "Up to three 2D planes of data (e.g. RGBA, Y+UV, Y+U+V)"; "It is an immutable snapshot".
- Import converts "the current image contents of source into the color space descriptor.colorSpace with unpremultiplied alpha. This may result in values outside of the range [0, 1]. If clamping is desired, it may be performed after sampling. Note: This is described like a copy, but may be implemented as a reference to read-only underlying data plus appropriate metadata to perform conversion later."
- Sampling (§6.5): "the result is in the color space set by colorSpace"; "It is implementation-dependent whether ... the sampler (and filtering) is applied before or after conversion"; for multi-plane sources "the sampler is used to sample each underlying texture separately, prior to conversion from YUV to the specified color space."
- §3.11: "WebGPU does not provide color management"; conversions do not clamp; out-of-gamut premultiplied values output to a visible canvas are undefined.
- Expiry: HTMLVideoElement source → "expires (is destroyed) automatically in a task after it is imported" (automatic expiry task; import in the same rVFC/rAF task). VideoFrame source → "expires (is destroyed) when, and only when, the source VideoFrame is closed." The UA may also return the *same* GPUExternalTexture object if the same frame is re-imported with the same descriptor ("renewing ownership").
- Descriptor: `required (HTMLVideoElement or VideoFrame) source; PredefinedColorSpace colorSpace = "srgb";` — no flipY/rotation options (rotation comes from the VideoFrame itself; see §7.2).
- Binding a regular `GPUTextureView` to a `texture_external` slot is allowed (2d, one mip level, `rgba8unorm`/`bgra8unorm`/`rgba16float`) — Chrome 137 (https://developer.chrome.com/blog/new-in-webgpu-137, 2025-05-26; Intent to Ship 2025-04-02 https://groups.google.com/a/chromium.org/g/blink-dev/c/_uF6EV6PXRo/m/J0543SHmAwAJ).

### 1.3 How Chrome actually imports (verified from Chromium/Dawn source, main 2026-10-10)
File: https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/modules/webgpu/external_texture_helper.cc

Zero-copy is taken **only if all** hold:
```
si_supports_zero_copy = frame->HasSharedImage() && shared_image usage has SHARED_IMAGE_USAGE_WEBGPU_READ
                        && GpuMemoryBufferType != SHARED_MEMORY_BUFFER   // TODO crbug 425634684
zero_copy = si_supports_zero_copy && frame->format() == media::PIXEL_FORMAT_NV12
            && adapter has DawnMultiPlanarFormats
            && DstColorSpaceSupportedByZeroCopy(dst)   // only "srgb" and "display-p3"
```
with the comment: "TODO(crbug.com/40227105): Support HDR color space and color range in generated wgsl shader to enable all color space for zero-copy path." Zero-copy creates two views on the NV12 shared image: plane0 `R8Unorm`, plane1 `RG8Unorm`. It is platform-agnostic in Blink; what differs per OS is whether the decoder output is an NV12 shared image with WEBGPU_READ (D3D11 NV12 on Windows, IOSurface '420v' on macOS, AHardwareBuffer/DMA-buf on Android/Linux — the per-OS producers themselves were **UNVERIFIED** in this pass).

Everything else (software I420 in shared memory, P010 / 10-bit, 4:2:2/4:4:4 formats, RGBA frames, `srgb-linear` destination) goes through the **1-copy path**: the frame is drawn/copied into a recycled RGBA shared image sized to `natural_size` via `PaintCanvasVideoRenderer::CopyVideoFrameToSharedImage` (if `CanUseCopyVideoFrameToSharedImage` and visible==natural) or `PaintCanvasVideoRenderer::Paint` + `RasterSharedImage`. Format is N32 (8-bit RGBA/BGRA): "High bit depth formats should also use F16, but do not yet." (only `PIXEL_FORMAT_RGBAF16` sources get F16). So 10-bit video loses precision to 8 bits before WebGPU sees it.

Color conversion constants handed to Dawn: YUV→RGB 3x4 matrix from Skia `SkColorMatrix::YUVtoRGB` (bit-depth aware), gamut matrix (src primaries → dst primaries via XYZ D50), 7-parameter skcms source transfer function and destination inverse transfer. `doYuvToRgbConversionOnly = IsSameGamutAndGamma(src, dst)` (same primary ID and identical 7 transfer params). Important detail from `ui/gfx/color_space.cc` (main 2026-10-10): `GetTransferFunction` maps `BT709`, `SMPTE170M`, `BT2020_10` to the **sRGB** curve ("use the same transfer function as sRGB, which will allow more optimization"), so a BT.709-tagged SDR frame imported into an `"srgb"` external texture is **YUV-matrix-only** (no pow() per sample). PQ/HLG sources get skcms PQ/HLG parametrisations (`skcms_TransferFunction_makePQ/HLG`), so the full decode→gamut→encode path runs. There is **no tone mapping and no clamp** anywhere in this path.

Tint lowering (https://raw.githubusercontent.com/google/dawn/main/src/tint/lang/core/ir/transform/multiplanar_external_texture.cc, main 2026-10-10): each `texture_external` becomes plane0 `texture_2d<f32>`, plane1 `texture_2d<f32>`, and a uniform params struct {numPlanes, doYuvToRgbConversionOnly, yuvToRgbConversionMatrix mat3x4, srcTransferFunction{mode,A..G}, dstTransferFunction, gamutConversionMatrix mat3x3, sampleTransform mat3x2, loadTransform mat3x2, samplePlane0RectMin/Max, samplePlane1RectMin/Max, apparentSize, plane1CoordFactor, ootfParam}. `textureSampleBaseClampToEdge` → coords × sampleTransform, clamp to each plane's half-texel rect, `textureSampleLevel(plane0, s, c, 0)` **and** `textureSampleLevel(plane1, s, c, 0)` with the **caller's sampler**, then `vec4(y, uv, 1) * matrix`, then (unless conversion-only) transfer decode (mode 0 gamma / 1 HLG / else PQ) → gamut → encode. `textureLoad` → `min(coords, apparentSize)`, `round(loadTransform*c)`, `textureLoad(plane0, c, 0)` and plane1 at `c * plane1CoordFactor` (integer fetch, **no chroma filtering**). `textureDimensions` → `apparentSize` (= `displayWidth/Height`, fixed in Chrome 133: https://developer.chrome.com/blog/new-in-webgpu-133, 2025-01-29). Rotation/mirroring from `VideoFrame` metadata are folded into `sampleTransform`/`loadTransform` (Dawn `ExternalTexture.cpp`, main 2026-10-10).

**Cost model (zero-copy NV12 → srgb):** per sample = 2 bilinear fetches (Y at full res, UV at half res) + one 3x4 multiply; chroma upsampling is whatever your sampler does (bilinear if `filter: 'linear'`). PQ/BT.2020 source: + per-sample PQ EOTF, 3x3 gamut, sRGB OETF. 1-copy path: a Skia draw into RGBA8 before your pass (+ an extra GPU pass and 8-bit quantisation), then a single fetch per sample.

### 1.4 HDR through importExternalTexture (verified, with gaps)
- Destination color spaces exposed to JS: Chrome validates `colorSpace` against `PredefinedColorSpace` (`predefined_color_space.idl`, main 2026-10-10): `srgb`, `display-p3`, `srgb-linear`/`display-p3-linear` (behind `ColorSpacePredefinedLinearSpaces`; shipped for the canvas in Chrome 155-156, see §2), `rec2020`/`rec2100-hlg`/`rec2100-pq` (behind `CanvasHDR`, "not in any spec"), `rec2100-linear` (behind `ColorSpaceRec2100Linear`). Zero-copy only for `srgb`/`display-p3`.
- Values > 1 can come out (spec allows it; Chrome does not clamp), but HDR10 (P010) frames take the 1-copy 8-bit path. gpuweb discussion #4384 (2023-11-17/20, https://github.com/gpuweb/gpuweb/discussions/4384): Chromium engineer: "HDR support is still missing from the 0-copy GPUExternalTexture path (crbug 1330230)"; "The 1-copy path falls back to 8-bit and only handles predefined color space conversion"; `bt2020`/`bt2100-pq` not exposed to the JS WebGPU context.
- gpuweb issue #5236 "copyExternalImageToTexture/importExternalTexture: Add HDR headroom parameter" (opened 2025-06-30 by ccameron, **open**, Milestone 2, last activity 2025-11-21, https://github.com/gpuweb/gpuweb/issues/5236): no headroom/tone-mapping control exists today; kainino's test (2025-07-18): Chrome and Firefox did not preserve HDR values from an HDR PNG via `copyExternalImageToTexture`; WebKit (mwyrzykowski, 2025-07-24): "Safari supports HDR video import for p420, p422, and p444 formats", imports losslessly, prefers not to auto-tone-map.
- Chrome 121 added `display-p3` as external-texture color space (https://developer.chrome.com/blog/new-in-webgpu-121, last updated 2024-01-18).

### 1.5 `copyExternalImageToTexture(VideoFrame)` (verified)
- Spec (§ GPUQueue.copyExternalImageToTexture, index.bs 2026-10-10): destination `usage` must include **both** `RENDER_ATTACHMENT` and `COPY_DST`; dimension 2d; sampleCount 1; "plain color format supporting RENDER_ATTACHMENT and be a unorm/unorm-srgb or float/ufloat format". Options: `source.origin`, `source.flipY`, `destination.colorSpace` (`srgb`/`display-p3` per MDN), `destination.premultipliedAlpha`. Allowed formats (MDN https://developer.mozilla.org/en-US/docs/Web/API/GPUQueue/copyExternalImageToTexture): r8unorm, r16float, r32float, rg8unorm, rg16float, rg32float, rgba8unorm(-srgb), bgra8unorm(-srgb), rgb10a2unorm, rgba16float, rgba32float (+ rg11b10ufloat with the feature).
- Chrome implementation (`gpu_queue.cc` `CopyFromVideoElement`, main 2026-10-10): builds the **same** ExternalTexture (zero-copy or 1-copy) and runs Dawn `CopyTextureForBrowser` with an external-texture pipeline; Dawn's `CopyTextureForBrowserHelper.cpp` (main 2026-10-10) is a **render pipeline** (`@vertex` + `@fragment fn copyExternalTexture` doing `textureSampleBaseClampToEdge`, TriangleList). Source alpha is assumed premultiplied. So it is never cheaper than drawing your own full-screen triangle; for non-NV12 frames it is one extra pass on top of the 1-copy.
- Support (BCD): Chrome 113 (VideoFrame source 116), Chrome Android 121, Safari 26 (VideoFrame source 26), Firefox 141 partial — **VideoFrame source not supported in Firefox** (BCD `videoframe_source: firefox False`; Firefox `Queue.cpp` main only handles ImageBitmap/HTMLImageElement/OffscreenCanvas; WebKit comment in #5236: Safari supports only 32bpp sources for this call).

## 2. HDR output from a WebGPU canvas

### 2.1 Spec (verified, index.bs 2026-10-10)
- `GPUCanvasConfiguration { format; usage = RENDER_ATTACHMENT; viewFormats; PredefinedColorSpace colorSpace = "srgb"; GPUCanvasToneMapping toneMapping = {}; alphaMode = "opaque" }`. "WebGPU allows all of the color spaces in the PredefinedColorSpace enum."
- Supported context formats: «bgra8unorm, rgba8unorm, rgba16float» — "must be supported ... regardless of the given device". No `-srgb` canvas formats (use `viewFormats`).
- `"standard"`: clamp in the screen's color space to [0,1] (spec example (1.035,-0.175,-0.140) → sRGB (1,0,0), but displayable on a P3 screen). `"extended"`: "Color values in the extended dynamic range of the screen are unchanged, and all other color values are projected to the extended dynamic range of the screen. Note: This projection is often accomplished by clamping color values in the color space of the screen to the interval of values that the screen is capable of displaying, which may include values greater than 1."
- Feature-detection note: UAs that do not implement tone mapping should **omit** the member so `getConfiguration()` reveals it; "If an implementation exposes this member and a `high` dynamic range, it should render the canvas as an HDR element."
- Meaning of "extended": values are in the configured `colorSpace` (sRGB or P3, gamma-encoded unless `-linear`), extended range, no browser tone mapping (ccameron's explainer: "does not introduce any non-trivial (clamping) tone mapping behaviors"; no PQ/HLG; no HDR metadata; https://ccameron-chromium.github.io/webgpu-hdr/EXPLAINER.html, undated). Issue #4919 (https://github.com/gpuweb/gpuweb/issues/4919, opened 2024-10-15, closed not-planned 2026-07-28): ccameron 2025-07-29: current "extended" is "just clamp everything that doesn't fit"; display headroom "won't be reliably exposed"; future configurable tone-mapping curves planned; closed because it "needs to get standardized at the broader Color on the Web CG".
- Consequence for PQ/HLG content: **you** must decode PQ/HLG to linear light, scale against your chosen reference white, and write extended-range values (gamma-encoded sRGB/P3 or `-linear`) into an `rgba16float` canvas; the browser clamps to what the display can show.

## 4. Zero-copy / pass-through at native resolution

- **`copyExternalImageToTexture(VideoFrame → canvas.getCurrentTexture())`**: legal iff `configure({usage: RENDER_ATTACHMENT | COPY_DST})` (spec: `RENDER_ATTACHMENT` is not auto-added when `usage` is set). Cost in Chrome = the external-texture import (zero-copy or 1-copy) **plus** Dawn's internal full-screen render pipeline (`CopyTextureForBrowserHelper.cpp`). It is a convenience, not a shortcut: at best equal to your own single pass, and it cannot upscale with anything but the sampler.
- **Canvas 2D `drawImage(VideoFrame)`** (Chrome `media/gfx/paint_canvas_video_renderer.cc`, main 2026-10-10): GPU-backed frames are wrapped as a Skia YUVA image (`SkYUVAInfo` from the shared-image format, 4:2:0/4:2:2/4:4:4 plane configs) and drawn by Skia with YUV→RGB in its shader — one GPU draw, no CPU copy; software frames are converted with libyuv on the CPU (`I420/I422/I444[Alpha]ToARGB`, 10-bit variants) then uploaded. "Zero-copy on which platform" beyond this is **UNVERIFIED**.
- **`<video>` via a generator** uses the media compositor path (overlays possible), but the generator APIs are split: Chrome has only `MediaStreamTrackGenerator` (94), Safari only `VideoTrackGenerator` (18), Firefox neither (BCD).
- **Overlay promotion of a WebGPU canvas**:
  - Windows (`components/viz/service/display/dc_layer_overlay.cc`, main 2026-10-10): "`DCLayerOverlayProcessor` is only used for video overlays and low-latency canvas overlays" — a quad is only considered if `is_video_frame` or `IsLowLatencyRendering(resource)`; `GPUCanvasContext` has no desynchronized/low-latency option (grep of `gpu_canvas_context.cc` finds none), so a WebGPU canvas is **not** promoted on Windows. Full delegated compositing on Windows is still not the default (`viz/common/features.cc`: Windows default `kLimitToUi`, "TODO(crbug.com/324460866): Windows does not fully support full delegated compositing").
  - macOS (`webgpu_swap_buffer_provider.cc`): WebGPU swap-chain shared images get `SHARED_IMAGE_USAGE_SCANOUT` ("safe to allow SharedImages created with WebGPU usage ... to be used as overlays ... forces that SharedImage to be backed by an IOSurface"); `ca_layer_overlay.cc` turns any overlay-candidate `TextureDrawQuad` into its own CALayer (carrying `nearest_neighbor_filter` and `hdr_metadata`). So on macOS the window server can present and scale the canvas directly.
  - ChromeOS: scanout allowed behind a kill-switch feature. Android/Linux: not visible in the files read — **UNVERIFIED**.
- **Compositor scaling (CSS size ≠ canvas size)**: the display compositor already draws the canvas quad once per frame; applying a scale to that quad is free relative to an extra render pass. `image-rendering: pixelated` maps to the quad's `nearest_neighbor` flag (seen in `ca_layer_overlay.cc`). Filtering is bilinear otherwise; nothing fancier is available from CSS.
- `OffscreenCanvas.transferToImageBitmap` / `ImageBitmapRenderingContext`: not re-read in this pass — **UNVERIFIED** as a cost comparison.

## 5. Limits/behaviours for a 1-pass fullscreen upscaler

- **Canvas texture usages**: default `RENDER_ATTACHMENT`; `STORAGE_BINDING` is allowed when the format supports storage: `rgba8unorm` and `rgba16float` do in core, `bgra8unorm` only with `bgra8unorm-storage` (write-only in Chrome ≥ 143). Chrome specifics (`gpu_canvas_context.cc`, main 2026-10-10): on **Android**, `STORAGE_BINDING` or a BGRA canvas forces an internal copy to the swap texture ("Storage images are not supported on some AHB/gralloc versions"); on **macOS** `rgba8unorm` forces a copy ("not natively supported by MacOS's compositor"); on **Linux** BGRA forces a copy (mesa interop bug). Preferred canvas format (`blink gpu.cc`): **`rgba8unorm` on Android and Linux, `bgra8unorm` elsewhere**. Conclusion: a fragment pass into the canvas is the only path without an extra blit on every platform; compute output needs its own storage texture + blit except where the canvas can be storage without a copy (Windows/macOS with `bgra8unorm-storage`, or `rgba16float`).
- **textureGather**: available on `texture_2d<f32/i32/u32>` (4 texels, `@const component`, optional `@const offset`); not on `texture_external` → to use gather on video you need the 1-copy/RGBA route or your own copy.
- **Sampling in fragment**: `textureSampleBaseClampToEdge` and `textureLoad` are the only external-texture reads; both are usable in fragment and compute (no derivative requirement). (WGSL stage rules for `textureSample` vs `textureSampleLevel` not re-quoted here.)
- **Immediates (push constants)**: Chrome 149-150 (https://developer.chrome.com/blog/new-in-webgpu-149-150, 2026-06-17): `requires immediate_address_space;`, `var<immediate> ...;`, `passEncoder.setImmediates(rangeOffset, data)`, `layout: 'auto'` infers `immediateSize`; validation errors became `OperationError` in 151-152. Not in Safari/Firefox (BCD has no entry; **UNVERIFIED** beyond Chrome). Otherwise: uniform buffers + `writeBuffer` (2× faster since Chrome 144, https://developer.chrome.com/blog/new-in-webgpu-144, 2026-01-07).
- **Bind groups per frame**: because each import yields a (possibly new) `GPUExternalTexture`, you create a bind group per frame in Chrome (Blink creates a new Dawn ExternalTexture, two views and a params uniform buffer per call; no GPU copy in the zero-copy case). The spec permits UAs to hand back the same object for the same frame; WebKit does this for `HTMLVideoElement` sources (`GPUDevice.cpp` `updateExternalTexture` when the media identifier matches).
- **Timestamps on mobile**: available where Vulkan reports `timestampComputeAndGraphics`; 100 µs quantisation everywhere unless the developer flag; results arrive via `resolveQuerySet` + buffer map (no sync read).
- **VideoFrame lifetime**: the external texture expires exactly when the `VideoFrame` is closed, so `close()` must happen **after** `queue.submit()` of the command buffer that samples it; conversely you may keep a frame open and reuse its external texture/bind group across several presents (unlike HTMLVideoElement imports, which die at end of task). WebCodecs: "Authors are encouraged to call close() on output VideoFrames immediately when frames are no longer needed ... can cause decoding to stall" (https://w3c.github.io/webcodecs/, 2026-10-10).
- **Chrome 116**: video playback is no longer throttled when `importExternalTexture()` is called (https://developer.chrome.com/blog/new-in-webgpu-116, last updated 2023-08-08).

## 6. Mobile / Safari specifics and 4:4:4

- **Safari 26 WebGPU + external textures** (WebKit main 2026-10-10): `GPUExternalTextureDescriptor.source` is `(HTMLVideoElement or WebCodecsVideoFrame)` (IDL); `ExternalTexture.mm` wraps a `CVPixelBuffer` (IOSurface, ownership tagged to the web process) into two Metal textures; `BindGroup.mm` maps CV formats to per-plane Metal formats (`R8Unorm`/`RG8Unorm` for 8-bit biplanar 4:2:0/4:2:2/4:4:4, `R16Unorm`/`RG16Unorm` or Apple `MTLPixelFormatYCBCR10_{420,422,444}_2P` for 10-bit `x420/x422/x444`, packed `p420/p422/p444`) and picks the YCbCr→RGB matrix from `kCVImageBufferYCbCrMatrixKey` (709/601/240M/2020), i.e. the conversion is done in the shader like Chrome. WebKit's WGSL compiler supports `textureDimensions`, `textureLoad(texture_external, vec2<integer>)` and `textureSampleBaseClampToEdge` (`TypeDeclarations.rb`, main). WebKit statement (issue #5236, 2025-07-24): HDR video import supported for p420/p422/p444, lossless, no auto tone-map; "some other 10-bit formats have bugs".
- **WebCodecs 4:4:4 formats**: `VideoPixelFormat` includes `I444`, `I444P10`, `I444P12` (WebKit `VideoPixelFormat.idl`, main; Chrome `webcodecs/video_frame.cc` maps `I444`→`PIXEL_FORMAT_I444`, `I444P10`→`YUV444P10`, `I444P12`→`YUV444P12`, plus `I444A`, `I444AP10`). The MDN article still lists only I420/I420P10/I420P12/I420A/I422/I444/NV12/RGBA/RGBX/BGRA/BGRX (https://developer.mozilla.org/en-US/docs/Web/API/VideoFrame/format). `VideoFrame.format`: Chrome 94, Firefox 130, Safari 16.4 (BCD).
- **What Chrome reports for GPU frames** (`CopyToFormat`, main): externally-sampled shared images report `NV12`/`I420` if that is the native format, otherwise `RGBX`; non-mappable frames with bit depth ≠ 8 → `format === null`. So an HEVC Rext 4:4:4 hardware frame on Windows will not show up as `I444`.
- **Who produces 4:4:4 frames**: Windows D3D11 HEVC Rext (`media/gpu/windows/supported_profile_helpers.cc`, main): 8-bit 4:4:4 → `DXGI_FORMAT_AYUV`, 10-bit → `Y410`, 12-bit → `Y416` (4:2:2 → YUY2/Y210/Y216; 4:2:0 → NV12/P010/P016); Intel GUIDs for the Rext profiles. Community changelog (secondary, https://github.com/StaZhu/enable-chromium-hevc-hardware-decoding): 8-bit 4:4:4 since Chrome 117, original chroma retained since 125, NVIDIA Rext since 137 (driver ≥ 572.16), Apple Silicon 8/10-bit 4:2:2/4:4:4 in hardware. **None of these are NV12 → in Chrome they take the 1-copy RGBA8 path for WebGPU** (chroma already full-res, no interpolation needed, but 10/12-bit precision is lost). macOS Chrome VideoToolbox 4:4:4 output format and Android MediaCodec 4:4:4: **UNVERIFIED**.
- **Chroma upsampling, who does it**: zero-copy NV12 → the UV plane is fetched with *your* sampler at half resolution: bilinear sampler = bilinear chroma; `textureLoad` = nearest chroma (plane1 coordinate scaled by `plane1CoordFactor`, no filtering). 1-copy path → Skia's YUV→RGB (bilinear chroma via its YUVA image sampling) before your shader; you then see RGBA. 4:4:4 → no upsampling anywhere.

## 7. Addendum: modern WGSL/WebGPU techniques, shipping status 2025-2026

### 7.1 `subgroups` incl. quad ops in fragment shaders
- WGSL spec (index.bs 2026-10-10): the `subgroups` enable-extension makes "subgroup built-in values, subgroup built-in functions, and quad built-in functions" valid; it does **not** restrict them to compute. Helper invocations: "Helper invocations may be active or inactive in an operation. That is, on some devices helper invocations may participate in subgroup operations, while on other devices they may not." Quad ops: "If one of these functions is called in non-uniform control flow, then the result is an indeterminate value"; "Derivatives are an implicit type of quad operation." `subgroup_invocation_id` in fragment "may not be dense. The implementation may assign some lower-numbered IDs to helper invocations."
- Chrome: subgroup built-ins in **compute and fragment** since Chrome 129 (blog, "subgroup_size built-in is currently buggy in fragment shaders" at that time), shipped Chrome 134; Dawn Vulkan requires the fragment-stage subgroup bit (so devices lacking it do not get the feature at all). Backends: D3D12 SM 6.0 wave ops; Metal Apple6+/Mac2; Vulkan requirements in §3.1 (Adreno/Mali per-driver coverage **UNVERIFIED**). Safari: WebKit main gates on Metal3; BCD says not in Safari 26. Firefox: unimplemented (bug 1955417).
- Practical restriction for an upscaler: use quad ops only in uniform control flow; treat helper-lane participation as device-dependent; `@subgroup_size` is compute-only.

### 7.2 `textureLoad(texture_external, vec2<i32|u32>)`
Spec/Tint overload verified (§1.1); Chrome lowering = two integer fetches (Y, UV×plane1CoordFactor), no filtering; `textureDimensions` returns `displayWidth/Height` (Chrome 133 fix). Safari: supported per WebKit `TypeDeclarations.rb` (`[T < ConcreteInteger].(texture_external, vec2[T]) => vec4[f32]`). Firefox: external textures exist since **Firefox 144** (BCD `importExternalTexture` 144 partial, `videoframe_source` 144; pref `dom.webgpu.external-texture.enabled` true on Windows/macOS in `StaticPrefList.yaml` main; meta bug 1827116 still NEW, https://bugzilla.mozilla.org/rest/bug/1827116, last change 2026-09-14). Import options: there is no `flipY`/`rotation` on `importExternalTexture`; `copyExternalImageToTexture` has `flipY`; orientation comes from `VideoFrame.rotation`/`flip` (Chrome 138 only per BCD) which Chrome folds into the external texture's transforms.

### 7.3 Pipeline-overridable constants
`override` + `constants` in `GPUProgrammableStage` are core WebGPU (present in every shipping implementation since WebGPU 1.0; `createRenderPipeline` BCD: Chrome 113, Safari 26, Firefox 141). No primary measurement of specialisation cost was found — **UNVERIFIED**; each distinct constant set is a distinct pipeline compile by construction.

### 7.4 `bgra8unorm-storage` and compute → canvas
See §5. Preferred format is `bgra8unorm` on Windows/macOS/ChromeOS, `rgba8unorm` on Android/Linux (Chrome source). On Android any `STORAGE_BINDING` canvas incurs an internal copy; on macOS `rgba8unorm` incurs one; `rgba16float` + `STORAGE_BINDING` is format-legal in core (storage-capable format) but Android still copies. No Chrome document measuring compute-to-canvas vs render pass was found — **UNVERIFIED**.

### 7.5 Compatibility mode
- Shipped in Chrome **146** (Intent to Ship 2026-01-13, https://groups.google.com/a/chromium.org/g/blink-dev/c/N3RlLGCOTJ4; blog https://developer.chrome.com/blog/new-in-webgpu-146, 2026-02-25: opt-in via `requestAdapter({featureLevel: "compatibility"})`, Android OpenGL ES 3.1 first, ChromeOS GLES and Windows D3D11 "exploring"); origin trial 139–145 (https://developer.chrome.com/blog/new-in-webgpu-139, 2025-07-30: 31 % of Windows Chrome users lack D3D FL 11.1+, 15 % of Android lack Vulkan). BCD: `featureLevel` Chrome 146 partial. WebKit: "it is not anticipated that this feature will ship in Safari"; Mozilla: "has not committed to implementing it yet".
- Restrictions (proposal https://github.com/gpuweb/gpuweb/blob/main/proposals/compatibility-mode.md, main 2026-10-10) relevant here: texture-view dimension must be declared at creation; no `cube-array`; views of one texture in a draw must match aspect/mips/swizzle; no `sample_mask`/`sample_index`; no RG storage formats; lower limits; `maxStorageTexturesInFragmentStage` default **4**, `maxStorageBuffers/TexturesInVertexStage` default 0; no `linear`/`sample` interpolation; no `bgra8unorm-srgb`; no `textureLoad` on depth textures; no `@interpolate(flat)`; a cap on texture+sampler combinations per stage (**external textures count**, so `texture_external` is supported); no multisampled `rgba16float`/`r32float`; no `dpdxFine/dpdyFine/fwidthFine`. `textureGather` is not listed as restricted. `subgroups` is an optional feature and simply absent on GLES adapters (Dawn exposes it per backend capability).

### 7.6 `adapter.info`, power preference, battery
- `GPUAdapter.info`: Chrome 127 (`device.adapterInfo` 132), Safari 26, Firefox 141 partial (BCD). Chrome (`gpu_adapter.cc`, main): exposes `vendor`, `architecture`, `subgroupMinSize/MaxSize`, `isFallbackAdapter`; `device`, `description`, driver, backend, `powerPreference`, memory heaps **only with `chrome://flags/#enable-webgpu-developer-features`** (not fuzzed; simply omitted). - Dual-GPU: Chrome's GPU-process adapter filter (`webgpu_decoder_impl.cc` `CanUseAdapter`) requires the adapter to support importing shared images (IOSurface/AHardwareBuffer `SharedTextureMemory` or `SupportsExternalImages`), rejects blocklisted adapters, and applies a forced power preference from command line; what happens when the video decoder's GPU differs from the WebGPU adapter is **UNVERIFIED** from this pass (the zero-copy test above would then fail at the shared-image level and fall to the 1-copy path, but I did not confirm that).
- `navigator.getBattery()`: Chrome 38 (secure context since 103), Firefox 43–52 (removed), Safari never (BCD; MDN https://developer.mozilla.org/en-US/docs/Web/API/Navigator/getBattery).

### 7.8 Intermediate formats and tiler guidance
- Features: `rg11b10ufloat-renderable` (Chrome 113 incl. Android; Safari 26 always; Firefox not per BCD), `float32-filterable` (Chrome 119; Safari conditional on `supports32BitFloatFiltering`), `float32-blendable` (Chrome 132; Safari 26; Firefox 158 partial), `texture-formats-tier1` (Chrome 142; Safari 26.2 per BCD; r16unorm/rg16unorm/rgba16unorm renderable + storage), tier2 (Chrome 142; read-write storage). `rgb10a2unorm` is core renderable.
- Qualcomm "Adreno GPU on Mobile: Best Practices" (https://docs.qualcomm.com/bundle/publicresource/80-78185-2/topics/mobile_best_practices.md, read 2026-10-10, undated page): "Prefer fragment shaders to compute shaders when possible" (compute must write results to memory before the next kernel; fragment uses "Adreno's concurrent resolve hardware"); compute shaders "almost certainly disable UBWC"; fragment UAV writes disable LRZ; best render-target formats: R10G10B10A2 ("the hardware is optimized for this format"), R11G11B10 if no alpha, RGBA16 only if needed; "Use strict half-precision types as much as possible" (up to 2× perf/power for mediump).
- Arm: Vulkanised 2025 "Vulkan Best Practices for Mobile Development" (Pete Harris, 2025-02-11/13, https://www.vulkan.org/user/pages/09.events/vulkanised-2025/T18-Pete-Harris-Arm-MobileBestPractices.pdf): tile-based essentials, "Minimize tile memory use of DRAM", "Make good use of loadOp, storeOp, and resolve" — no explicit compute-vs-fragment image-store statement in the deck. Arm blog "Picking the most efficient load/store operations" (2019-10-15) covers LOAD/STORE/DONT_CARE and transient attachments only. Khronos Vulkan Guide TBR page: transient attachments live in tile memory, "some GPUs can avoid allocating any physical system memory". Arm's explicit guidance on storage-image writes vs colour attachments (AFBC loss) was **not found in a primary source** in this pass.
- Chrome Android uses Vulkan for WebGPU (blocklist: "ARM, Qualcomm, and Intel GPUs are supported on Android 12+ on Vulkan"; Imagination on Android 16+), GLES 3.1 only in compatibility mode; `TRANSIENT_ATTACHMENT` usage shipped Chrome 146 ("lets render pass operations stay in tile memory").
